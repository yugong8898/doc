## 目标与范围

本次仅加固 `wlyd-workflow` 的流程规则、验证脚本和配套流程文档，解决 REQ-170 首次执行暴露的流程问题：

1. 多需求共用 `.md/temp/workflow-state.md` 导致恢复对象错误。
2. `quick-verify.sh` 只读取暂存区，与“不暂存、不提交”的阶段性开发约束冲突。
3. 代码在阶段 4 审查后继续变化时，流程没有强制回退到复审。
4. 仅做局部断言会遗漏带注释的完整 Vue 模板编译问题。
5. 技术方案约定的最小改动范围无法由机器检查。

不修改 REQ-170 业务代码、不重写既有需求产物、不引入提交或自动暂存行为。

## 设计决策

采用“需求目录为唯一工作区”的方式：阶段状态与正式阶段产物直接存放在原始 PRD 同级目录。`.md/temp/` 只允许承载可删除的草稿和一次性中间文件，不再作为需求状态的默认位置。

状态文件记录当前需求目录、允许改动文件、阶段 4 审查时的代码 diff 指纹和最近门禁证据。后续恢复必须由用户提供 PRD 文件或需求目录；若未提供，workflow 先列出候选需求目录并要求选择，禁止读取全局唯一状态文件猜测需求。

## 需求级工作区

标准布局如下：

```text
.md/需求/<需求目录>/
├── <原始PRD>.md
├── workflow-state.md
├── 需求文档-<需求标识>.md
├── 代码分析-<需求标识>.md
├── 技术方案-<需求标识>.md
├── 实施记录-<需求标识>.md
├── 审查报告-<需求标识>.md
├── 测试用例-<需求标识>.md
├── bug跟踪-<需求标识>.md
└── 交付报告-<需求标识>.md
```

`workflow-state.md` 新增以下字段：

```markdown
## 工作区
- 需求目录：.md/需求/<需求目录>/
- 原始 PRD：<相对路径>

## 阶段3范围约束
- 允许改动文件：
  - <项目相对路径>

## 阶段4审查指纹
- 审查基线：<仓库与 HEAD>
- 审查 diff SHA-256：<git diff 输出摘要的哈希>
- 审查后代码变更：否
```

阶段 3 完成时记录允许改动文件，来源只能是已确认技术方案。阶段 4 完成时记录审查对象的 diff 指纹。恢复、进入阶段 5 或声明阶段 4 通过前，重新计算指纹；不同则自动将阶段 4 状态改为“待复审”，并要求先复审当前 diff。

## 验证门禁

`quick-verify.sh` 采用显式 scope，不再隐式只读暂存区：

```text
bash .md/scripts/quick-verify.sh --scope unstaged
bash .md/scripts/quick-verify.sh --scope staged
bash .md/scripts/quick-verify.sh --scope both
bash .md/scripts/quick-verify.sh --scope unstaged --files path/a.vue,path/b.ts
```

默认 scope 为 `both`。脚本必须：

1. 显示本次实际参与校验的文件；没有匹配文件时以非零退出，禁止“全绿但未检查”。
2. 对 JS、TS、Vue 文件检查新增 `console.log`。
3. 检查大文件、`git diff --check` 与改动统计。
4. 在存在 ESLint 配置时，对目标文件运行项目 ESLint；若被忽略，报告“文件被忽略”并以非零退出，不将其记为通过。
5. 不执行 `git add`、`git reset`、提交或其他 Git 写操作。

无法运行项目 lint 或类型检查时，状态文件必须记录项目、命令、错误摘要和首次发现日期；该问题不能伪装为门禁通过。

## 审查与范围闭环

阶段 3 的门禁接收技术方案中的允许文件清单。发现范围外文件时，脚本以非零退出，并列出文件；只有在实施记录写明原因且用户确认扩大范围后，才允许更新技术方案和清单。

阶段 4 的审查报告必须记录：审查基线、审查文件、diff 指纹、执行的验证命令及结果。任何阶段 4 之后的代码变更——包括回退、精简、修复 P0——都使原审查结论失效，至少重跑一次针对当前 diff 的独立审查。

## 模板编译验证

对本次改变模板、样式或 Vue 注释结构的 `.vue` 文件，验证必须使用原始文件内容，不得删除注释、替换节点或只抽取片段后再宣称完整模板可编译。

优先顺序：

1. 项目现有的单文件组件编译、类型检查或构建命令。
2. 针对原始 SFC 的定向编译检查，保留编译器默认的注释处理行为。
3. 有公共布局或动态组件容器变更时，对该完整容器一并编译。

模板编译失败属于 P0；修复后必须重新运行同一条红绿验证和阶段 4 审查。

## 兼容与迁移

旧需求的 `.md/temp/workflow-state.md` 不自动迁移、不覆盖。首次运行新流程时：

- 用户提供需求目录或 PRD：直接在其同级查找或创建 `workflow-state.md`。
- 用户只说“继续”：列出 `.md/需求/*/workflow-state.md` 的候选项，要求选择。
- 旧 `.md/temp/workflow-state.md` 存在：仅提示其为旧式状态文件，不自动加载。

`role-workflow.md` 与 `docs/wlyd-workflow-upgrade/` 中涉及状态位置、门禁和阶段出口的说明必须同步更新；WLYD rules、业务代码、知识库不在本次改造范围。

## 验收标准

1. 两个需求可各自拥有独立 `workflow-state.md`，执行“继续”不会误读另一需求。
2. 未暂存的目标文件可被门禁实际检查；无匹配文件、被 ESLint 忽略或 lint 失败均不能返回成功。
3. 门禁不会暂存、撤销暂存、提交或修改业务代码。
4. 技术方案外的改动文件被报告并阻止阶段出口。
5. 阶段 4 后修改任一代码文件时，状态自动要求复审，不能直接进入阶段 5。
6. 带注释的完整 Vue 模板编译失败能被定向验证发现。
