# 总体方案

## 一、为什么需要升级

### 当前问题

现有 `wlyd-workflow` 是单向流水线（6 阶段依次走完），实际开发中存在：

- 需求理解有偏差，到编码时才发现
- 技术方案漏了需求里的某条规则
- 代码改动偏离了技术方案
- 测试用例和代码对不上，bug 反复出现
- 需求中途变更后，前面的结论没有真正回退重做

**本质缺的不是流程骨架，而是"每一步做完都回头对一遍"的保障机制。**

### 升级目标

在每个阶段完成后增加系统性回验，防止以下偏差一路传递到最终交付：

- 需求理解遗漏或误解
- 代码分析没有覆盖需求涉及的页面、模块或端
- 技术方案漏掉业务规则、边界条件或异常处理
- 代码实现偏离技术方案，或混入未说明的额外改动
- 测试用例与需求、代码无法对应
- Bug 修复后没有验证原问题和受影响的回归范围

最终交付的判断依据不是"阶段走完"，而是"需求、方案、代码、测试和缺陷记录能够相互追踪，并且满足交付门禁"。

## 二、核心机制概览

### 验证闭环

```text
现在的流程：
需求 → 方案 → 编码 → 审查 → 提测 → 交付
（一路走到底，中途偏差无法及时发现）

升级后的流程：
执行阶段
  ↓
生成产物
  ↓
对照上一阶段锚点逐条验证
  ↓
发现偏差？
  ├─ 没有偏差 → 进入下一阶段
  ├─ 可修正偏差 → 修正后重新验证
  ├─ 需求不明确 → 暂停并确认
  └─ 高风险问题 → 回退到对应阶段
```

每个阶段不是只检查自己有没有完成，而是检查**自己有没有正确承接上一阶段的结论**。

### 需求追踪

从阶段 0 开始给需求规则编号（`R-*`），形成追踪链：

```text
R-001：编辑页允许修改费用字段
  → 影响文件：edit.vue
  → 技术方案：方案 3.1
  → 代码位置：edit.vue:120
  → 测试用例：TC-001, TC-004
  → 测试结果：通过
  → Bug：无
```

这是解决"需求理解偏差"和"最终交付无法证明"的核心手段。

### 变更回退

需求变更后不能继续沿用旧结论，必须：

- 判断变更影响范围
- 回退到对应阶段重新评估
- 更新追踪表中的受影响条目

例如：新增端、新增接口、修改业务规则 → 回退到阶段 0。

## 三、方案定位

本次升级基于两份模型结论：

- `qoder.workflow.md`：上层设计方案，定义"为什么做、解决什么问题、采用什么工作模式"
- `cursor.workflow.md`：执行落地规范，定义"每阶段怎么验证、如何回退、什么条件下允许交付"

最终采用：

```text
qoder 的上层设计
+
cursor 的验证闭环
+
需求版本管理
+
证据链
+
Bug 根因回退
+
正式测试 / 开发自测区分
+
循环终止保护
```

## 四、总体结构

```text
wlyd-workflow
├── 阶段0 需求分析
│   └── 验证：需求原文 → 需求理解
├── 阶段1 代码分析
│   └── 验证：需求理解 → 代码分析
├── 阶段2 技术方案
│   └── 验证：需求理解 + 代码分析 → 技术方案
├── 阶段3 编码执行
│   └── 验证：技术方案 → 代码
├── 阶段4 代码审查
│   └── 验证：需求 + 方案 + 代码 → 审查结果
├── 阶段5 测试基线与覆盖对齐
│   └── 验证：需求 ↔ 测试用例 ↔ 代码
└── 阶段6 测试执行与 Bug 修复循环
    └── 验证：测试用例逐条通过 → 最终交付
```

## 五、实施原则

### 不过早做复杂自动化

当前问题主要不是"缺少脚本"，而是：

- 不知道什么叫验证通过
- 不知道什么时候必须回退
- 不知道哪些问题阻塞交付
- 不知道需求如何映射到代码和测试

先把状态模型和门禁设计正确，再决定哪些部分值得自动化。

### 渐进式推进

不要一次性重写所有流程，建议按以下顺序推进：

1. 先统一状态、阶段和回退规则
2. 增加统一验证协议
3. 增加 R-* 需求编号
4. 逐步增加其他机制
5. 用真实需求试运行
6. 根据实际负担调整复杂度

### 分层追踪

不是所有需求都要跑完整流程：

- **所有需求**：最小追踪记录（需求编号 → 修改文件 → 验证结果）
- **复杂/高风险需求**：完整追踪矩阵（增加需求版本、影响范围、方案、用例、Bug、证据）

### 双工作模式

- **默认模式**：复杂需求逐阶段确认
- **自动模式**：简单、低风险需求允许自动推进，但不能跳过任何门禁

## 六、与现有流程的关系

本次升级不是完全推翻重来，而是在现有基础上增强：

| 现有组件 | 升级后的关系 |
|---|---|
| `wlyd-workflow` | 增加验证闭环、阶段 5、阶段 6、追踪体系和交付门禁 |
| `wlyd-requirement-change-analysis` | 阶段 0 调用，增加 R-* 编号生成 |
| `wlyd-review` | 阶段 4 调用，增加三向审查和验证记录合并 |
| `role-qa-checklist` | 阶段 5 调用，增加覆盖矩阵和 AI 用例标注 |
| `code-analyzer` | 阶段 1 调用，保持不变 |
| `role-pm`、`role-architect`、`role-coder`、`role-reviewer` | 各阶段调用，保持不变 |

## 七、预期效果

升级后，可以实现：

- 每个阶段都有明确的验证标准和通过条件
- 需求变更后自动触发回退和重新评估
- 需求、方案、代码、测试用例和 Bug 可以相互追踪
- 测试失败后根据根因决定回退位置，而不是直接改代码
- 正式测试和开发自测结论明确分离
- 最终交付有完整的证据链和门禁检查
