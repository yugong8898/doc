# 统一验证协议

## 一、为什么需要统一验证协议

当前问题：

- 验证结果只有"通过"或"不通过"，缺少中间状态
- 不知道验证过程中发现了什么问题、如何修正
- 没有证据支撑验证结论
- "已修正后通过"和"首次通过"被混为一谈

统一验证协议解决：

- 标准化验证记录格式
- 明确验证状态分类
- 保留偏差和修正过程
- 要求提供验证证据

## 二、验证记录格式

每个阶段的验证记录统一使用以下结构：

```text
验证状态：通过 / 已修正后通过 / 待确认 / 阻塞
对照锚点：
检查范围：
发现偏差：
修正内容：
验证证据：
重新验证结果：
是否允许进入下一阶段：
```

### 字段说明

| 字段 | 说明 | 必填 |
|---|---|---|
| 验证状态 | 验证结论，见下文状态定义 | 是 |
| 对照锚点 | 验证时对照的上一阶段产物 | 是 |
| 检查范围 | 验证了哪些内容 | 是 |
| 发现偏差 | 验证过程中发现的问题 | 如有偏差必填 |
| 修正内容 | 如何修正偏差 | 如有偏差必填 |
| 验证证据 | 证据类型和位置 | 是 |
| 重新验证结果 | 修正后的复验结果 | 如有修正必填 |
| 是否允许进入下一阶段 | 是/否 | 是 |

## 三、验证状态定义

### 通过

**含义**：首次验证即符合标准，没有发现偏差。

**使用场景**：
- 需求理解文档完整覆盖需求原文
- 代码分析覆盖所有涉及页面和模块
- 技术方案覆盖所有需求规则
- 代码实现符合技术方案
- 测试用例覆盖所有需求

**示例**：

```text
验证状态：通过
对照锚点：需求原文
检查范围：R-001 至 R-005（5 条需求规则）
发现偏差：无
修正内容：无
验证证据：逐条对照检查，需求文档第 2-4 章
重新验证结果：未执行
是否允许进入下一阶段：是
```

### 已修正后通过

**含义**：首次验证发现偏差，修正后复验通过。

**重要**：不能直接改写成普通"通过"，必须保留偏差和修正记录。

**使用场景**：
- 需求理解遗漏了某个页面，补充后通过
- 代码分析遗漏了公共组件，补充后通过
- 技术方案遗漏了边界处理，补充后通过
- 代码实现有额外改动，说明原因后通过

**示例**：

```text
验证状态：已修正后通过
对照锚点：需求理解文档
检查范围：涉及页面和模块
发现偏差：需求涉及查看页（view.vue），但代码分析只分析了编辑页（edit.vue）
修正内容：补充 view.vue 的代码分析，识别同步展示逻辑
验证证据：代码分析文档第 3.2 节
重新验证结果：通过
是否允许进入下一阶段：是
```

### 待确认

**含义**：验证过程中发现不确定项，需要用户或相关方确认后才能继续。

**使用场景**：
- 需求原文中字段名不明确
- 接口路径不确定
- 新旧字段是否复用不确定
- 测试预期与需求冲突
- 保存接口是否需要新增参数不确定

**处理**：必须暂停当前阶段，等待确认后再继续。不能自行猜测或跳过。

**示例**：

```text
验证状态：待确认
对照锚点：需求理解文档
检查范围：接口和字段
发现偏差：需求提到"新接口新字段"，但未说明是复用旧接口的字段还是新接口有同名字段
修正内容：无法自行判断
验证证据：需求文档第 5.2 节
重新验证结果：未执行
是否允许进入下一阶段：否（需确认后再继续）
```

### 阻塞

**含义**：存在环境、权限、接口、数据或其他无法继续的问题。

**使用场景**：
- 测试环境不可用
- 接口未部署
- 数据不可用
- 权限不足
- 依赖的其他需求未完成

**处理**：标记阻塞原因，等待问题解决。

**示例**：

```text
验证状态：阻塞
对照锚点：测试用例
检查范围：TC-001 至 TC-005
发现偏差：测试环境接口返回 503
修正内容：无法在当前环境执行测试
验证证据：接口日志，错误截图
重新验证结果：未执行
是否允许进入下一阶段：否（需环境恢复后再测试）
```

## 四、验证证据类型

验证证据不能只写"已检查"，必须提供具体证据类型和位置。

### 证据类型清单

| 证据类型 | 说明 | 示例 |
|---|---|---|
| 需求原文 | 需求文档路径和章节 | `.md/需求/【Cxxx.x】xxx.md` 第 3 节 |
| 代码路径和行号 | 具体文件和行号 | `edit.vue:120-150` |
| git diff | 代码变更记录 | `git diff HEAD` 输出 |
| ESLint 输出 | 静态检查结果 | `npx eslint xxx.vue` 结果截图 |
| 类型检查输出 | 类型检查结果 | `tsc --noEmit` 结果 |
| 构建输出 | 构建检查结果 | `npm run build` 结果 |
| 测试截图 | 实际执行截图 | 测试环境截图 |
| QA 反馈 | QA 提供的测试报告 | QA 反馈邮件/文档 |
| 接口响应 | 接口返回数据 | 接口日志或截图 |
| 手工操作记录 | 手工验证步骤 | 操作步骤和结果描述 |

### 证据记录示例

```text
验证证据：
- 对照文件：.md/temp/需求文档-C147.9.md
- 对照条目：R-001～R-006
- 检查方式：逐条人工核对
- 证据位置：技术方案文档第 4.2 节
- 偏差记录：R-004 缺少异常处理
- 修正证据：技术方案文档第 4.2.3 节（新增）
- 复验方式：再次逐条核对
```

## 五、验证协议在各阶段的应用

### 阶段 0：需求分析

**对照锚点**：需求原文

**检查范围**：
- 需求原文每条规则
- 涉及范围
- 其他影响
- 测试要求

**常见偏差**：
- 遗漏"其他影响"章节
- 遗漏示例中的边界条件
- 未区分 AI 推断和已确认需求

### 阶段 1：代码分析

**对照锚点**：需求理解文档

**检查范围**：
- 需求涉及的每个页面、模块和端
- 横向影响（查看、列表、详情、对账、付款）
- 公共组件、接口封装

**常见偏差**：
- 只分析编辑页，遗漏查看页
- 只分析 PC 端，遗漏移动端
- 遗漏公共组件

### 阶段 2：技术方案

**对照锚点**：需求理解 + 代码分析

**检查范围**：
- 每条 R-* 是否有方案条目
- 边界和异常规则是否有处理策略
- 待确认项是否仍然阻塞编码

**常见偏差**：
- 方案遗漏某条需求规则
- 方案遗漏边界处理
- 方案遗漏异常处理

### 阶段 3：编码执行

**对照锚点**：技术方案

**检查范围**：
- 方案中的每个改动点
- 是否存在方案之外的额外改动
- 权限、校验、状态、旧逻辑保留

**常见偏差**：
- 方案有但代码没有实现
- 代码有但方案没有说明
- 旧逻辑被直接删除

### 阶段 4：代码审查

**对照锚点**：需求 + 方案 + 代码

**检查范围**：
- 需求、方案、代码三向一致性
- 横向页面和多端影响
- 权限、校验、状态、旧逻辑

**常见偏差**：
- 需求有但方案没有
- 方案有但代码没有
- 代码有但需求和方案都没有
- 只审查局部 diff，遗漏完整 Vue 模板中的编译约束
- 审查完成后代码变化，但未使阶段 4 失效

### 阶段 5：测试基线与覆盖对齐

**对照锚点**：需求 + 测试用例 + 代码

**检查范围**：
- 需求 → 测试用例
- 测试用例 → 需求
- 测试用例 → 代码实现

**常见偏差**：
- 需求有但测试用例没有
- 测试用例有但需求没有
- 测试用例有但代码没有实现

### 阶段 6：测试执行与 Bug 修复循环

**对照锚点**：测试用例逐条结果

**检查范围**：
- 每条测试用例的执行结果
- 失败用例的根因分类
- Bug 修复后的回归范围

**常见偏差**：
- Bug 修复后只测原问题，未完成回归
- 环境问题被误判为实现缺陷
- 需求偏差被误判为实现缺陷

## 六、验证记录的存储

验证记录存储在当前需求目录 `workflow-state.md` 的"验证闭环记录"表格中。阶段 4 还必须记录实际受检文件、完整代码 diff 的 SHA-256、审查时间与复审失效原因：

```markdown
## 验证闭环记录

| 阶段 | 锚点 | 验证结果 | 偏差数 | 修正次数 | 证据 |
|---|---|---|---|---|---|
| 阶段0 需求分析 | 需求原文 | 通过 | 0 | 0 | 需求文档第 2-4 章 |
| 阶段1 代码分析 | 需求理解 | 已修正后通过 | 1 | 1 | 代码分析文档第 3.2 节 |
| 阶段2 技术方案 | 需求+代码分析 | 通过 | 0 | 0 | 技术方案文档全文 |
```

## 七、验证不通过时的处理

### "已修正后通过"的处理

1. 记录发现的偏差
2. 修正产物
3. 重新验证
4. 更新验证记录
5. 允许进入下一阶段

### "待确认"的处理

1. 记录不确定项
2. 暂停当前阶段
3. 请求用户或相关方确认
4. 确认后更新产物
5. 重新验证
6. 允许进入下一阶段

### "阻塞"的处理

1. 记录阻塞原因
2. 暂停当前阶段
3. 等待阻塞解除
4. 阻塞解除后重新验证
5. 允许进入下一阶段
