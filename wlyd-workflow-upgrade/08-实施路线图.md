# 实施路线图

## 一、实施原则

### 渐进式推进

不要一次性重写所有流程，建议按顺序渐进推进：

- 每次只增加一个机制
- 用真实需求验证效果
- 根据实际负担调整复杂度
- 发现问题及时回滚

### 保持可回滚

每一步实施前：

- 备份现有 Skill 文件
- 记录修改内容
- 保留回滚方案
- 出现问题立即回滚

### 三端同步

每次修改必须同步三端：

- `.cursor/skills/wlyd-workflow/SKILL.md`
- `.qoder/skills/wlyd-workflow/SKILL.md`
- `.codebuddy/skills/wlyd-workflow/SKILL.md`
- `.md/prompts/role-workflow.md`（可选）

修改后执行校验：

```bash
bash ai-tooling-seed/scripts/verify-rules-sync.sh .
```

### 步骤 6：增加三种测试结论类型

**验收标准**：


## 四、分阶段实施建议

如果不能一次性投入 4-5 天，可以分阶段实施：

### 第一阶段：核心验证机制（步骤 1-3）

**目标**：建立验证闭环和需求追踪基础。

**时间**：1-2 天

**价值**：每个阶段有明确验证标准，需求可以追踪。

### 第二阶段：测试覆盖和循环（步骤 4-6）

**目标**：拆分测试阶段，增加 Bug 修复循环。

**时间**：2-3 天

**价值**：测试用例可以和需求对应，Bug 修复有明确回退规则。

### 第三阶段：增强和试运行（步骤 7-10）

**目标**：增强证据链，实际验证流程可用性。

**时间**：1 天

**价值**：验证有证据支撑，流程复杂度经过实际验证。

## 五、风险和应对

### 风险 1：流程过于复杂，日常使用负担重

**应对**：

- 优先使用轻量追踪，只有复杂需求使用完整矩阵
- 支持自动推进模式，简单需求可快速通过
- 验证记录可以简化，不必每次都写完整

### 风险 2：与现有 Skill 衔接出现问题

**应对**：

- 步骤 3 重点测试与 `wlyd-requirement-change-analysis` 的衔接
- 步骤 4 重点测试与 `role-qa-checklist` 的衔接
- 步骤 5 重点测试与 `wlyd-review` 的衔接
- 发现问题及时调整调用方式

### 风险 3：阶段 6 循环逻辑复杂，容易出错

**应对**：

- 步骤 5 实施后先暂停，用真实需求测试
- Bug 分类和回退规则从简单情况开始支持
- 循环终止保护必须实现，避免无限循环

### 风险 4：三端同步出现漂移

**应对**：

- 每个步骤完成后立即同步三端
- 每次同步后执行校验脚本
- 发现漂移立即修复

## 六、回滚方案

### 回滚触发条件

- 实施后发现严重 Bug
- 流程复杂度过高，日常使用受影响
- 与现有 Skill 衔接失败
- 三端同步持续漂移

### 回滚步骤

1. 恢复备份的 Skill 文件
2. 删除新增的状态和产物文件
3. 执行三端同步校验
4. 通知相关人员回滚原因

### 回滚后处理

- 记录失败原因
- 调整实施方案
- 重新评估实施时机
