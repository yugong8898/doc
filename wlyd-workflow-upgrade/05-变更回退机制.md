# 变更回退机制

## 一、为什么需要变更回退

### 当前问题

需求中途变更后，常见的错误处理方式：

- 直接在现有代码上增量修改，不重新评估影响
- 继续沿用已经失效的技术方案
- 测试用例不更新，基于旧需求验证新实现
- 追踪表不更新，无法判断哪些改动对应新需求

### 变更回退解决

- 识别变更类型和影响范围
- 判断最低回退阶段
- 重新执行受影响阶段
- 更新追踪表和版本记录
- 确保新需求有完整证据链

## 二、变更触发条件

以下情况必须触发变更回退，不能继续沿用旧结论：

### 触发条件清单

| 变更类型 | 示例 | 是否触发回退 |
|---|---|---|
| 新增端 | 原本只做 PC，现在要加移动端 | 是 |
| 新增页面或模块 | 原本只改编辑页，现在要加查看页 | 是 |
| 新增接口 | 原本复用旧接口，现在要调新接口 | 是 |
| 新增字段 | 原本字段 A，现在还要加字段 B | 是 |
| 修改字段口径 | 原本字段 A 存金额，现在改成存费率 | 是 |
| 修改业务规则 | 原本已完成可改，现在改成不可改 | 是 |
| 修改交互结果 | 原本保存后跳转，现在改成不跳转 | 是 |
| 用户指出遗漏 | 原本没说查看页，现在说查看页也要改 | 是 |
| 测试预期变化 | 原本测试预期 A，现在改成预期 B | 是 |
| 发现旧逻辑误用 | 原本认为复用旧字段，实际是新字段 | 是 |
| 纯文案调整 | 改个标题、提示语 | 否 |
| 代码优化 | 性能优化、代码重构 | 否 |
| 注释补充 | 补充代码注释 | 否 |

### 判断标准

如果变更满足以下任一条件，必须触发回退：

```text
□ 影响需求范围（端、页面、模块、接口、字段）
□ 影响业务规则（权限、状态、金额、校验）
□ 影响交互结果（保存、提交、跳转、提示）
□ 影响测试预期（用例步骤、预期结果）
□ 原有理解被证明错误
```

## 三、回退规则

### 回退阶段映射

| 变更类型 | 最低回退阶段 | 原因 |
|---|---|---|
| 新增端、页面、模块 | 阶段 0 | 需求范围变化，需要重新分析整体影响 |
| 新增接口或字段 | 阶段 0 | 接口和字段影响方案和实现，需要从需求重新确认 |
| 修改业务规则 | 阶段 0 | 业务规则变化，需要重新理解需求和边界 |
| 修改字段口径 | 阶段 0 | 字段含义变化，影响整体设计 |
| 修改交互结果 | 阶段 0 | 交互变化，影响需求理解和用户体验 |
| 发现遗漏页面或模块 | 阶段 1 | 代码分析不完整，需要补充分析 |
| 发现遗漏横向影响 | 阶段 1 | 横向搜索不完整，需要补充 |
| 发现技术方案遗漏 | 阶段 2 | 方案不完整，需要补充方案 |
| 发现代码实现错误 | 阶段 3 | 实现错误，需要修复代码 |
| 测试用例或预期变化 | 阶段 5 | 测试基线变化，需要重新对齐 |

### 回退流程

```text
发现变更
  ↓
记录变更内容
  ↓
判断变更类型
  ↓
确定最低回退阶段
  ↓
识别受影响的 R-*
  ↓
更新需求版本
  ↓
回退到指定阶段
  ↓
重新执行受影响阶段
  ↓
更新追踪表
  ↓
更新变更日志
```

## 四、变更记录

### 变更通知模板

用户补充信息时，AI 必须先输出：

```text
【收到需求变更】

变更内容：xxx
变更类型：新增 / 修改 / 废弃
影响判断：新增端 / 新增接口 / 修改业务规则 / ...
最低回退阶段：阶段 0 / 阶段 1 / 阶段 2 / ...
受影响的 R-*：R-001, R-003
受影响的用例：TC-001, TC-004
需要重新检查：范围分析 / 技术方案 / 代码实现 / 测试用例

下一步：回退到阶段 X，重新执行...
```

### 变更日志格式

在 `workflow-state.md` 或追踪矩阵中维护变更日志：

```markdown
## 需求变更日志

| 版本 | 变更时间 | 变更内容 | 影响的 R-* | 回退阶段 | 处理结果 |
|---|---|---|---|---|---|
| R0 | 2026-09-01 | 初始需求 | R-001~R-005 | - | - |
| R1 | 2026-09-03 | 新增移动端范围 | R-001, R-004 | 阶段 0 | 已重新分析，更新方案 |
| R2 | 2026-09-05 | 修改保存校验规则 | R-003 | 阶段 2 | 已更新方案和实现 |
| R3 | 2026-09-06 | 废弃字段 B，改用字段 C | R-002 | 阶段 0 | 已重新确认，更新代码 |
```

## 五、版本管理

### 需求版本

从 `R0` 开始，每次需求变更递增版本：

```text
R0：初始需求
R1：新增移动端范围
R2：修改保存校验规则
R3：废弃字段 B，改用字段 C
```

### 测试版本

从 `T0` 开始，每次测试基线变化递增版本：

```text
T0：初始测试用例
T1：新增移动端测试用例
T2：修改保存校验测试预期
```

### 版本与追踪表的关系

追踪表必须包含需求版本字段：

```markdown
| 需求版本 | 需求编号 | 需求摘要 | 代码位置 | 测试用例 | 测试结果 |
|---|---|---|---|---|---|
| R1 | R-001 | 编辑页允许修改费用字段（新增移动端） | edit.vue:120, app/edit.vue:88 | TC-001, TC-005 | 通过 |
| R0 | R-002 | 已完成状态不可修改 | edit.vue:88 | TC-002 | 通过 |
| R2 | R-003 | 保存失败时保留用户输入（新增校验） | edit.vue:150 | TC-003, TC-006 | 通过 |
```

## 六、回退实施步骤

### 示例 1：新增移动端（回退到阶段 0）

**变更**：原本只做 PC 端编辑页，现在要加移动端编辑页。

**回退流程**：

1. 记录变更：新增移动端范围
2. 判断类型：新增端
3. 确定回退：阶段 0
4. 识别影响：R-001（编辑页功能）
5. 更新版本：R0 → R1
6. 回退阶段 0：重新分析需求，补充移动端部分
7. 重新阶段 1：分析移动端代码
8. 重新阶段 2：补充移动端技术方案
9. 重新阶段 3：实现移动端代码
10. 重新阶段 4：审查移动端代码
11. 重新阶段 5：补充移动端测试用例
12. 重新阶段 6：执行移动端测试
13. 更新追踪表：R-001 增加移动端相关内容
14. 更新变更日志

### 示例 2：发现遗漏查看页（回退到阶段 1）

**变更**：原本只分析了编辑页，但需求实际要求查看页也要展示该字段。

**回退流程**：

1. 记录变更：发现遗漏查看页
2. 判断类型：发现遗漏页面
3. 确定回退：阶段 1
4. 识别影响：R-001（字段展示）
5. 更新版本：R0 → R1
6. 回退阶段 1：补充查看页代码分析
7. 重新阶段 2：补充查看页技术方案
8. 重新阶段 3：实现查看页代码
9. 重新阶段 4：审查查看页代码
10. 重新阶段 5：补充查看页测试用例
11. 重新阶段 6：执行查看页测试
12. 更新追踪表：R-001 增加查看页相关内容
13. 更新变更日志

### 示例 3：修改保存校验规则（回退到阶段 2）

**变更**：原本保存时不校验，现在要求保存时必须校验费用不为空。

**回退流程**：

1. 记录变更：修改保存校验规则
2. 判断类型：修改业务规则
3. 确定回退：阶段 2（如果已进入阶段 3 以上）
4. 识别影响：R-003（保存逻辑）
5. 更新版本：R1 → R2
6. 回退阶段 2：补充保存校验方案
7. 重新阶段 3：实现保存校验代码
8. 重新阶段 4：审查保存校验代码
9. 重新阶段 5：补充保存校验测试用例
10. 重新阶段 6：执行保存校验测试
11. 更新追踪表：R-003 更新方案和实现
12. 更新变更日志

## 七、回退的例外情况

### 不回退的情况

以下情况可以增量修改，不必回退：

- 纯文案调整（不影响业务逻辑）
- 代码优化（不改变功能）
- 注释补充（不改变代码行为）
- Bug 修复（按 Bug 分类回退，不按变更回退）

### 部分回退的情况

如果变更只影响部分需求，可以部分回退：

- 只回退受影响的 R-*
- 不影响的 R-* 保持不变
- 更新追踪表中受影响的行
- 保留不受影响的行

## 八、回退与 Bug 修复的区别

| 对比项 | 需求变更回退 | Bug 修复 |
|---|---|---|
| 触发原因 | 需求范围、规则、预期变化 | 测试失败 |
| 判断依据 | 变更类型 | Bug 根因 |
| 回退目标 | 重新理解需求或补充方案 | 修复代码或更新测试 |
| 版本变化 | 需求版本递增 | 需求版本不变 |
| 是否重新执行所有阶段 | 从回退阶段开始重新执行 | 只修复和回归 |

## 九、回退的验证

回退并重新执行后，必须验证：

```text
□ 变更内容已纳入新版本需求
□ 受影响的 R-* 已重新验证
□ 追踪表已更新
□ 变更日志已更新
□ 受影响的测试用例已更新
□ 所有受影响阶段已重新执行并通过验证
```

## 十、常见错误

### 错误 1：变更后不回退，直接增量修改

**问题**：原有方案基于旧需求，新增内容可能与旧方案冲突。

**正确**：识别变更，回退到对应阶段，重新评估。

### 错误 2：回退后不更新版本

**问题**：无法判断当前代码对应哪个版本的需求。

**正确**：每次回退都递增需求版本，更新变更日志。

### 错误 3：回退后不更新追踪表

**问题**：追踪表仍然基于旧需求，无法证明新需求已实现。

**正确**：回退后更新追踪表中受影响的 R-*。

### 错误 4：把 Bug 修复当成需求变更

**问题**：Bug 修复不应该修改需求版本。

**正确**：Bug 修复按 Bug 根因回退，需求变更按变更类型回退。
