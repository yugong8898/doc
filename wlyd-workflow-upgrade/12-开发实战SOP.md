# 开发实战 SOP：用 Harness Loop Graph 少返工、少犯错

> 目标：把「高效开发」落成**可执行的动作序列**，而不是原则。核心思路是三根支柱接管 AI 最容易出错的三个环节：
>
> - **Graph（图谱）** 决定改哪里 → 解决「漏改 / 改错地方」
> - **Harness（门禁）** 机器判定结果 → 解决「自认为改对了」
> - **Loop（回流）** 失败回退 + 教训沉淀 → 解决「同样的错反复犯」
>
> 配套图示：[`../harness-loop-graph/harness-loop-graph.md`](../harness-loop-graph/harness-loop-graph.md)

## 一、这套机制在防什么

| AI 高频失误 | 具体表现 | 由哪根支柱兜底 |
|---|---|---|
| 范围遗漏 | 只改调整页，漏掉查看页 / 列表页 / 移动端 / 公共组件 / 接口封装 | **Graph**（查库 + 九宫格横向搜索） |
| 脑补不确定项 | 字段名没确认就写死，接口路径靠猜 | **Loop**（待确认项强制暂停闸门） |
| 直接删除旧代码 | 替换逻辑时删掉原文，无法追溯、误伤隐藏业务 | **硬规则**（旧逻辑注释保留） |
| 验证靠自述 | 「已完成、已验证」但没有机器证据 | **Harness**（exit-code 门禁） |
| 来源不同默认同处理 | 相同公式不同触发来源，默认处理方式一样 | **需求拆解**（逐条拆原文，分别确认） |
| 多层架构规则误套 | 用物流线规则校验企服线代码（rpx / 条件编译 / 深层选择器） | **门禁分线**（按项目路径切换规则集） |
| 流程静默死亡 | 需求卡在待确认项，无人知晓（`C161` 曾卡两个月） | **Loop**（Stall 检测告警） |

## 二、五步闭环与三支柱

```
① Retrieve 检索上下文  →  ② Plan 接单确认 + 改动清单  →  ③ Act 最小改动
        ↑                                                        ↓
   ⑤ Learn 回流沉淀  ←  ④ Verify 机器门禁（exit≠0 不放行）
```

- 绿色线：**Graph** 汇入 ①（先查库再读码）
- 橙色线：**Harness** 被 ④ 调用（机器判定）
- 紫色线：④ 失败回退 ② / ③；⑤ 回到 ① 进入下一轮

**贯穿全程的三条硬规则**：逐条拆需求原文、不确定项必须显式列出、旧逻辑注释保留不删除。

## 三、开发前：接单与需求理解

**核心：需求不看标题，只拆原文。**

1. **逐条拆解**，把需求原文的每一句变成一条可执行规则，分配 `R-*` 编号（`R-001`、`R-002`…）
2. **特别关注易漏段落**：「涉及范围」「其他影响」「测试要求」「其他优化」、示例中的边界场景、字段初始值/修改后值/保存后值的差异
3. **识别业务范围**：是否涉及全流程运单、分次支付、司机对账、金额计算、多端（PC/H5/小程序/APP）
4. **输出接单确认**，动手前必须包含：
   ```
   需求理解：xxx
   涉及文件：xxx（角色：调整页 / 查看页 / 列表页 / 移动端 / 公共组件 / 接口封装）
   横向搜索已检查：□ 调整页 □ 查看页 □ 列表页 □ 对账页 □ 付款页 □ 移动端 □ 公共组件 □ 接口封装
   旧逻辑处理方式：注释保留 / 不涉及
   不确定项：问题 + 影响范围（有则必须等确认后再动手）
   ```
5. **有不确定项就停**：字段名、接口路径、字段口径、是否复用旧字段——一律进「待确认清单」，**不允许脑补实现**

> 返工成本最低的一步就是这一步：需求阶段的 1 个待确认项，拖到测试阶段就是一次完整返工。

## 四、动手前：先查库，再定影响范围

WLYD 已有全前端语义索引 `.repoWiki/`，**默认先查库，查不到才读源码**。

| 顺序 | 检索对象 | 拿什么 |
|---|---|---|
| 1 | `.repoWiki/kb/INDEX.md` | 确认改动落在哪个子项目 |
| 2 | `kb/<project>/README.md` | 项目地图、模块划分、**已知坑点** |
| 3 | `kb/<project>/views.md` `api.md` `components.md` | 定位具体文件条目 |
| 4 | `kb/<project>/views/**.md`、`modules/**.md` | 逐文件详情（`modules/` 为已精读深度文档，优先级最高） |
| 5 | `.repoWiki/maps/<project>-tree.md` | 同模块相邻文件，确认没有漏网的兄弟页面 |

- **路径映射**：源码 `logisticsweb/src/views/userBase/X.vue` → 文档 `kb/logisticsweb/views/userBase/X.md`
- **知识库滞后兜底**：对照 `.repoWiki/.sync-state.json` 锚点跑增量，只对未覆盖部分实读源码：
  ```bash
  git -C logisticsweb diff --stat <anchor> HEAD
  git -C logisticsweb log --oneline <anchor>..HEAD
  ```
- **九宫格横向搜索必须落痕迹**：调整页 / 查看页 / 列表页 / 对账页 / 付款页 / 移动端对应页 / 公共组件 / 接口封装 —— 每个格子写「已确认无影响」或「需改：文件路径」，**不写默认视为未做**
- **多端矩阵**：改 `logisticsweb` 的金额字段，必须同步检查 `wlyd-app-consigner` 对应页与 `web-match-owner` 的对账/付款页

## 五、开发中：最小改动的硬约束

1. **旧逻辑注释保留**：替换/隐藏/废弃旧 UI、旧逻辑、旧配置时，先注释并注明需求号与原因，再写新内容；**除非会导致编译或运行失败且无法用注释规避，否则不删**
2. **一次只改一个功能**：多个功能混改，出问题无法定位
3. **逻辑收进方法**：模板里不写复杂三元与判断，判断放 `methods`（便于审查与复用）
4. **注释只写「代码说不出的信息」**：枚举值/魔法数字的业务语义（如 `stmtStatus === 2（待审核）`）、业务约束、非显然的位置顺序；**不写复述方法名的废话注释**
5. **高风险改动额外自查**：
   - 金额：一律 `BigNumber` / `BNumber`，允许 ±0.01 误差；清零用字符串 `'0.00'` 不用数字 `0`
   - 权限校验、数据校验、状态判断：**只能补不能删**
   - 平台差异：用条件编译（`#ifdef H5` / `#ifndef H5`），不用运行时判断
   - `platformweb`：样式穿透用 `::v-deep` / `:deep()`，**禁用** `/deep/` 与 `>>>`
   - 企服线（`ai-platform/es-web`、`es-ops-platform`）：Vue 3 + TS + Ant Design Vue / Element Plus，**不套用**物流线的 `rpx`、uni-app 条件编译、Element UI 写法
6. **每改完一个文件**：立即跑 lint，输出完成自检，再进入下一个文件

## 六、提交前：机器门禁

> `.md/scripts/quick-verify.sh` 只扫描 `git diff --cached`，**必须先 stage 再跑**，否则会「全绿但什么都没检查」的假通过。

```bash
git add -A && git diff --cached --stat   # 先核对改动范围是否超出技术方案
bash .md/scripts/quick-verify.sh         # git状态 / console.log / 大文件 / ESLint / 改动统计
echo "exit=$?"                            # 0=通过；非 0=不放行
```

| 结果 | 处理 |
|---|---|
| `exit=0` | 允许标绿进入下一阶段 |
| `exit≠0`（ESLint 失败） | 回退修复，error 清零后重跑，未经修复不得继续 |
| 提示新 `console.log` / 大文件 | 确认是否调试残留；确需保留的在产物里记录原因，其余清除 |
| 项目未配 ESLint | 手动跑项目自身 lint，把输出贴进验证记录作为证据 |
| 改动落在企服线 | 追加 `npx tsc --noEmit` |

**范围外改动必须记录**：凡技术方案清单之外的改动，单独列出文件 + 原因，供审查判定是否必要。

## 七、出问题后：根因分类与回退

先分类再修，修错层级的返工最贵。

| 根因 | 判定 | 回退到 |
|---|---|---|
| 需求偏差 | 实现与已确认需求不一致 | 阶段 0（重新确认需求） |
| 方案遗漏 | 需求有、方案没覆盖 | 阶段 2 |
| 实现缺陷 | 方案正确、代码写错 | 阶段 3 |
| 测试问题 | 用例步骤或预期有误 | 阶段 5 |
| 环境问题 | 接口/数据/权限阻塞 | 标记阻塞，不硬修 |

**修复后必须回归**：原失败用例重跑 + 按影响范围回归（公共组件、接口封装、金额、权限、状态、多端），**不能只测原问题**。

**防死机制**：任一阶段停留超过 7 天或存在待确认项时，先弹停滞告警（阶段 / 停留天数 / 待确认数），由人明确选择继续、回退还是归档，**不得无声沿用旧结论推进**。

## 八、高频返工场景速查表

| 场景 | 防法 | 检查点 |
|---|---|---|
| 需求只看了标题 | 逐条拆原文 + `R-*` 编号 | 每条需求都能指到具体文件 |
| 不确定项没问就写 | 待确认清单强制暂停 | 清单为空才允许进编码 |
| 漏改查看页/移动端 | 九宫格横向搜索 + 查库 | 九格每格都有结论 |
| 误删旧逻辑 | 注释保留 + 注明需求号 | diff 里没有裸删除 |
| 字段口径理解错 | 金额/状态字段注明来源与口径 | 关键字段标注出处 |
| 多端表现不一致 | 条件编译 + 多端矩阵 | H5 / 小程序 / APP 各确认一次 |
| 金额精度问题 | BigNumber + ±0.01 容差 | 无裸浮点累加 |
| 企服线套错规则 | 按项目路径切换规则集 | 门禁自动分线 |
| 验证靠自述 | exit-code 门禁 | 有 `exit=0` 证据 |
| 需求卡死无人知 | Stall 检测 | 开需求时先看是否停滞 |

## 九、检查清单

**接单时**
```
□ 需求已逐条拆解并编号 R-*
□ 涉及文件已列全，含移动端与公共组件
□ 九宫格横向搜索已实际执行（非凭印象）
□ 不确定项已列出，未经确认不动手
□ 旧逻辑处理方式已明确（注释保留）
```

**改完时**
```
□ 只改了技术方案清单内的文件（范围外已单独记录）
□ 旧逻辑以注释保留，无裸删除
□ 金额走 BigNumber，状态/权限/校验逻辑未删
□ 条件编译已按平台区分
□ 平台规则未跨线套用（物流线 / 企服线）
□ ESLint 已过（exit=0）
□ git add -A && bash .md/scripts/quick-verify.sh 已过
□ 完成自检已输出（横向搜索 / 旧逻辑保留 / 不确定项 / 门禁）
```

**交付时**
```
□ 需求 ↔ 方案 ↔ 代码三向一致
□ 回归范围已按影响面推导并执行
□ 范围外改动已说明原因
□ 教训已回流（坑点 / 规则 / 知识库）
```
