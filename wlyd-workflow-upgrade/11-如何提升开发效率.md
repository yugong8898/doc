# 如何使用 Harness/Graph/Loop 提升开发效率

## 一、你现在的困惑

> "如何使用 harness graph loop 工程帮我提升开发效率，现在无从下手"

这个困惑很正常。Harness、Graph、Loop 听起来很高大上，但实际上就是：

- **Harness（测试驾驶舱）** = 自动化验证脚本
- **Graph（依赖图谱）** = 理解代码影响范围
- **Loop（反馈循环）** = 快速发现问题并修复

**关键问题**：这些概念太抽象，不知道从哪里开始。

## 二、你已经有的基础

✅ **AI 工具链**：Cursor + Qoder + CodeBuddy  
✅ **工作流 Skill**：`wlyd-workflow`（已升级到 7 阶段）  
✅ **完整文档**：`docs/wlyd-workflow-upgrade/`（11 个文档）

**缺少的**：把这些工具串联成可重复执行的工程化流程。

## 三、从简单到复杂的行动路线

### 🎯 阶段 1：先用 workflow 跑一个真实需求（今天就可以做）

**目标**：验证新流程是否好用，建立信心。

**操作**：

```bash
# 1. 在 Cursor 中输入
@wlyd-workflow 走流程，需求是 xxx

# 2. 按照提示逐阶段推进
阶段0：需求分析 → 生成 R-* 编号
阶段1：代码分析 → 理解影响范围
阶段2：技术方案 → 建立追踪矩阵
阶段3：编码执行 → 记录范围外改动
阶段4：代码审查 → 验证需求、方案、代码一致
阶段5：测试基线与覆盖对齐 → 检查测试覆盖
阶段6：测试执行与Bug修复循环 → Bug 分类、回归验证

# 3. 记录每个阶段的耗时和问题
- 哪个阶段耗时最长？
- 哪个阶段遇到了问题？
- 哪个阶段感觉没必要？
```

**选择需求**：
- ✅ 简单需求：修改文案、调整样式、小功能优化
- ❌ 复杂需求：新增页面、新增接口、多端改动

**预计时间**：2-3 小时

**收益**：
- 实际体验 R-* 编号、验证闭环、Bug 分类
- 发现流程中的不合理之处
- 建立对新流程的信心

---

### 🎯 阶段 2：建立最小验证脚本（明天可以做）

**目标**：每次改动后自动跑基础检查，这就是最简单的 **Harness**。

**操作**：

```bash
# 已为你创建好脚本
.md/scripts/quick-verify.sh

# 每次改完代码后运行；不要求手动暂存
bash .md/scripts/quick-verify.sh --scope unstaged --allow-files path/a.vue,path/b.ts

# 或者配置 git pre-commit hook
ln -s ../../.md/scripts/quick-verify.sh .git/hooks/pre-commit
# hook 场景应固定传入 --scope staged
```

**脚本功能**：
1. ✅ 检查 git 状态
2. ✅ 检查 console.log
3. ✅ 检查大文件
4. ✅ 运行 ESLint
5. ✅ 统计改动范围

**预计时间**：10 分钟配置

**收益**：
- 避免提交有问题的代码
- 每次改动都有基础验证
- 建立"验证驾驶舱"的雏形

---

### 🎯 阶段 3：使用代码依赖分析（本周可以做）

**目标**：改动前知道影响范围，这就是 **Graph**。

**操作**：

```bash
# 方式 1：使用现有 Skill
@code-analyzer 分析 src/pages/xxx.vue 的依赖关系

# 方式 2：安装依赖分析工具
npm install -g madge
madge --image graph.svg src/pages/xxx.vue

# 方式 3：使用 Cursor 的 @Codebase
@Codebase 这个组件被哪些页面引用？
```

**使用场景**：
- 修改公共组件前，查看哪些页面引用了它
- 修改接口封装前，查看哪些地方调用了它
- 修改工具函数前，查看影响范围

**预计时间**：1 小时学习

**收益**：
- 改动前知道影响范围
- 避免遗漏回归测试
- 建立"依赖图谱"意识

---

### 🎯 阶段 4：建立 Bug 反馈循环（2周内可以做）

**目标**：快速发现问题 → 修复 → 验证，这就是 **Loop**。

**操作**：

这个其实就是你刚升级的 `wlyd-workflow` 阶段6！

```bash
# 测试发现 Bug 后
@wlyd-workflow 从阶段6开始

# AI 会自动：
1. 记录 Bug（BUG-001）
2. 分类根因（需求偏差/方案遗漏/实现缺陷/测试问题/环境问题）
3. 决定回退阶段
4. 修复后执行原用例 + 回归用例
5. 更新 Bug 跟踪表
```

**关键**：缩短每次循环的时间
- ❌ 差的循环：发现 Bug → 几天后才修复 → 忘了要回归什么
- ✅ 好的循环：发现 Bug → 立即分类 → 修复 → 回归 → 关闭

**预计时间**：随开发自然形成

**收益**：
- Bug 不再积压
- 修复后不遗漏回归
- 建立"快速反馈"习惯

### 🎯 阶段 5：建立产物模板（1个月内可以做）

**目标**：标准化输出，减少重复劳动。

**操作**：

```bash
# 为常见产物创建模板
.md/templates/
├── 需求文档-模板.md
├── 技术方案-模板.md
├── 测试用例-模板.md
├── Bug跟踪-模板.md
└── 交付报告-模板.md

# workflow 自动使用模板
@wlyd-workflow 走流程，需求是 xxx
→ 自动从模板生成需求文档
```

**预计时间**：2-3 小时

**收益**：
- 每次输出格式一致
- 减少手工整理时间
- 建立"标准化"习惯

## 六、常见问题

### Q1：workflow 太复杂，能简化吗？

**A**：可以！试运行后根据实际体验调整：
- 简单需求可以跳过某些阶段
- 验证记录可以简化
- 追踪矩阵可以用轻量版

参考：`docs/wlyd-workflow-upgrade/08-实施路线图.md` 第五部分"风险和应对"

### Q2：验证脚本能检查什么？

**A**：当前已支持：
- Git 状态
- console.log
- 大文件
- ESLint

可以自己扩展：
- 类型检查（tsc --noEmit）
- 构建检查（npm run build）
- 单元测试（npm test）

### Q3：如何知道代码影响范围？

**A**：三种方式：
1. 使用 `@code-analyzer` Skill
2. 使用 `@Codebase` 搜索引用
3. 使用 `madge` 工具生成依赖图

### Q4：Bug 循环如何缩短？

**A**：关键是分类和回退：
- 需求偏差 → 立即回退阶段0，重新确认
- 实现缺陷 → 立即修复，运行回归
- 不要等到积累多个 Bug 再处理

### Q5：什么时候需要完整追踪矩阵？

**A**：判断标准：
- 简单需求（≤2 个文件）→ 轻量追踪
- 复杂需求（≥3 个文件或跨端）→ 完整矩阵
- 高风险改动（金额、权限、支付、状态）→ 完整矩阵

参考：`docs/wlyd-workflow-upgrade/04-需求追踪体系.md`
